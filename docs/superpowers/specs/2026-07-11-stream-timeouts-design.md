# 流式分段超时设计

## 目标

避免上游流式请求在首个响应字节迟迟不到或传输中途永久停顿时无限占用连接，同时保持现有非流式超时、Key 冷却和协议转换语义不变。

## 方案比较

### 方案 A：恢复单一 HTTP 读取超时

直接把 `httpx` 的 `read` 超时设置为 `request_timeout`。改动最小，但首字节等待和流中空闲只能使用同一个阈值，长推理模型容易被误杀。

### 方案 B：代理层分别控制首字节和流空闲时间

保留流式 HTTP 读取超时为无限，由代理层用同一个期限限制响应头和第一个上游响应体字节，再由共享流迭代器限制后续字节间隔。三个协议流共用相同计时逻辑，超时仍进入现有的失败记录与资源释放路径。

这是推荐方案。它直接解决问题，不引入熔断器或后台探测，并允许针对长推理和卡死连接设置不同阈值。

### 方案 C：首字节前预读并自动切换 Key

代理在返回下游响应前预读上游首块，超时则切换 Key 并重放请求。体验更完整，但会显著改变流建立流程，并增加重复请求、重复计费和非幂等工具调用的风险，本次不采用。

## 配置

在路由配置中增加两个全局字段：

- `stream_first_byte_timeout`：等待上游第一个响应字节的秒数，默认 `90`。
- `stream_idle_timeout`：收到首字节后允许的最大字节间隔，默认 `180`。

两个字段都必须大于 `0`。现有 `request_timeout` 继续控制连接建立、写入和非流式请求，不改变含义。

配置加载、示例配置、TUI 设置和使用文档同步支持这两个字段。旧配置缺少字段时自动使用默认值，不需要迁移版本。

## 数据流

1. 发起流式上游请求前创建首字节截止时间。
2. 等待响应头和读取第一块响应体时共用这个截止时间，不在响应头到达后重新计时。
3. 第一块到达后，后续每次读取使用 `stream_idle_timeout`。
4. 任一阶段超时都抛出带阶段信息的读取超时。
5. 现有流生命周期捕获异常、记录失败指标、增加 Key 失败计数、释放 Key 并关闭上游响应。

`request_timeout` 继续控制连接建立和请求写入。`stream_first_byte_timeout` 控制从发起请求到收到第一块响应体的总等待时间。

## 错误行为

- 响应头返回前超时时，下游流尚未建立，沿用现有重试和切 Key 逻辑。
- 响应头返回后超时时，关闭当前下游流并写入结构化运行日志。
- 已经建立下游响应后不自动重放请求，避免客户端收到重复事件。
- 超时按失败计入 Key 健康状态；达到现有阈值后进入临时冷却。
- 指标记录保留已收到的 Token、字节、首字节耗时和总耗时。
- 客户端主动断开继续沿用现有异常与清理行为，不改变为 Key 故障。

## 实现边界

- 在发送上游请求时限制响应头等待，并把同一个首字节截止时间交给流生成器。
- 在 `streaming.py` 提供一个共享异步迭代器，不在三个协议生成器中复制计时逻辑。
- 三个流生成器仅把首字节截止时间和空闲超时传给共享迭代器。
- 不增加依赖，使用 Python 标准库 `asyncio.timeout()`。
- 不增加完整熔断状态机、后台健康探测或中途自动故障转移。

## 测试

- 配置缺省值和非法非正数校验。
- 响应头超时会进入现有重试和切 Key 路径。
- 首块在阈值内到达时正常输出。
- 第一块超时会结束流、记录失败并释放 Key。
- 第一块成功但后续块超时时执行相同清理。
- Chat Completions、Anthropic Messages 和 Responses 三条流路径都使用共享超时迭代器。
