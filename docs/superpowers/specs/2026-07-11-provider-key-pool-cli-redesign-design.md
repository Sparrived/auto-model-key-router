# 供应商 Key 与模型池 CLI 重设计

## 目标

CLI 应反映真实配置层级：模型池属于供应商，Key 属于供应商中的一个模型池，本地模型通过 target 路由到供应商模型池。用户不应分别维护供应商、Key、模型池和探测状态之间的关联。

本次重设计保留现有配置结构和运行时约束，只重构交互流程与自动维护逻辑。

## 信息架构

供应商相关操作调整为供应商优先的层级：

```text
供应商
├─ 添加供应商
└─ 选择已有供应商
   ├─ 添加 Key
   ├─ 管理 Key
   ├─ 模型池
   ├─ Base URL / 路由设置
   └─ 删除供应商

模型设置
├─ 本地模型
├─ Target
├─ 路由模式
└─ 别名
```

模型池不再作为顶层入口。进入供应商后，后续 Key 和模型池操作均使用当前供应商，不重复选择供应商。

## 添加 Key

添加 Key 的主流程为：

```text
选择或创建供应商
→ 输入 Key 名称和 API Key
→ 调用新 Key 的 /models
→ 同步调用同供应商现有模型池的 /models
→ 使用最新模型集合分组
→ 确认该池启用的模型
→ 保存
```

新 Key 的模型集合与现有池最新的可用模型集合完全一致时，视为能力相同。集合只要存在增减，就不自动加入该池。

模型池名称不表达能力语义。供应商的第一个自动池命名为 `default`，后续依次命名为 `pool-2`、`pool-3`。用户可在模型池管理中重命名。

## 同步探测与决策

添加新 Key 前，程序重新探测同供应商所有现有池，避免使用陈旧记录错误创建新池。

- 恰好一个池完全匹配：新 Key 自动加入该池；
- 多个池完全匹配：先自动合并这些重复池，再把新 Key 加入保留池；
- 没有池匹配：自动创建下一个模型池；
- 新 Key 或任一现有池探测失败：停止自动分组，让用户选择任一现有池或新建池。

失败池保留历史记录，并在人工选择页面标记“本次探测失败、信息可能过期”。程序不得用失败池的旧记录执行自动匹配。

删除“刷新可用性”操作。探测由添加 Key、手动移动 Key 和冲突修复等会改变或需要确认能力分组的事件自动触发。

## 重复池合并

能力集合完全相同的多个池按以下规则自动合并：

- 保留供应商配置顺序最靠前的池名；
- 汇总所有 Key；
- 用户启用模型 `models` 取并集；
- 可用性、逐 Key 模型和路由探测状态使用本次最新结果；
- 所有指向被合并池的 target 重定向到保留池；
- 删除其余重复池。

合并后仍满足一个 Key 必须且只能属于一个模型池。

## 模型选择

模型确认页展示本次探测到的全量模型与当前 `models` 的并集。

- 当前 `models` 中的模型预先勾选；
- 新发现模型默认不勾选；
- 所有 Key 共同可用的模型正常显示；
- 仅部分 Key 可用的模型使用警告色；
- 已启用但本次未发现的模型保持勾选并使用警告色。

探测状态只提供决策依据，不自动删除用户启用状态。

## 管理操作

Key 管理保留：

- 开关；
- 重命名；
- 访客权限；
- 删除。

删除“替换 API Key”。凭证变更通过删除旧 Key、添加新 Key 完成，统一走自动探测和分组流程。

模型池管理只保留：

- 查看详情；
- 设置启用模型；
- 重命名；
- 手动移动 Key。

删除最后一个 Key 或把最后一个 Key 移出池时，程序自动删除空池、清理指向该池的 target，并删除已没有任何 target 的本地模型。不提供单独的“删除空池”按钮。

## 错误处理

- `/models` 探测失败必须显示具体 Key、池和错误摘要；
- 自动流程遇到任一相关探测失败时必须转人工选择，不得静默使用缓存；
- 人工取消时不保存 Key、池、模型或 target 的部分修改；
- 自动合并和移动必须在完整配置验证成功后一次性提交；
- 非交互模式继续拒绝无效的一 Key 多池或零池配置，并提示运行 `amkr` 修复。

## 测试

测试覆盖：

- 供应商优先菜单和上下文传递；
- 添加 Key 时同步探测新 Key 与同供应商所有池；
- 严格集合匹配、自动建池和自动命名；
- 多个匹配池的合并、target 重定向与 `models` 并集；
- 任一探测失败时转人工选择且取消不落盘；
- 全量模型显示、当前勾选、新模型默认未选和警告状态；
- 删除“刷新可用性”“替换 API Key”和“删除空池”入口；
- 删除或移动最后一个 Key 后的空池、target 和无 target 模型清理；
- 原有路由、Key 冷却、重试和统一模型行为不回归。
