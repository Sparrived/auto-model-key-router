# 模型池模型约束路由设计

## 问题

配置解析当前只使用模型池的 `keys`，忽略模型池的 `models`。因此，同一供应商下的模型 target 即使指向未启用该上游模型的池，该池中的 Key 仍会进入轮询，并可能向不支持该模型的上游发送请求而得到 404。

## 语义

模型池的 `models` 是该池启用模型的强制白名单。一个 target 只有同时满足以下条件才产生候选 Key：

- target 引用了存在的供应商和模型池；
- target 的 `upstream_model` 存在于该模型池的 `models` 中；
- Key 和 target 本身处于启用状态。

模型池缺少 `models`、`models` 不是数组或数组为空时，视为没有启用任何模型，不为任何 target 产生候选 Key。这是有意的严格语义，旧配置需要显式填写模型池的 `models`。

## 实现

在 `RouterConfig.from_dict` 解析供应商模型池时，同时保留池的启用模型集合。解析 `models[].targets` 时，以 target 的 `upstream_model` 检查该集合；不在集合中则跳过整个 target，不展开池内 Key。

过滤发生在配置解析阶段，因此 `ModelConfig.keys` 和 `KeyPool` 接收到的候选 Key 天然满足模型池约束。轮询、优先级、固定首个 Key、访客权限、冷却和重试逻辑保持不变，也不需要在每次请求时重复检查模型池。

`targets` 继续负责本地模型到上游模型的映射，模型池负责决定哪些 Key 有资格承载该上游模型。

## 错误处理

引用不存在的供应商或模型池仍按现有行为抛出配置错误。引用存在但未启用目标模型的池不会使配置加载失败，而是产生零个候选 Key；请求时沿用现有的“没有可用 key”响应。

## 测试

新增配置解析回归测试：同一供应商具有 A、B 两个池，A 未启用 `gpt-5.6`，B 已启用；同一模型同时配置两个 target 后，候选 Key 只能包含 B 池的 Key。

另覆盖模型池缺少 `models` 和 `models` 为空数组的情况，确认二者均不产生候选 Key。随后运行相关配置、KeyPool 和代理测试，并运行完整测试套件。
