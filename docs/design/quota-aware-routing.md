# 额度感知路由设计

> 状态：**设计稿，尚未实现**。本文的配置字段、模式、接口增量、采集器、运行时状态及验收均为提案；当前服务不能按本文配置工作。范围是单个真实模型的上游目标选择，不设计嵌套路由组、意图/难度路由或新的模型回退机制。

## 1. 目标与用户流程

**目标**：在现有模型路由的 `routing_mode` 中增加 `usage` 和 `pace`：前者按 AMKR 观察到的近时段实际发往各上游 Key 的调用次数分摊，后者在可验证的上游额度窗口内优先消耗「剩余比例相对剩余时间较多」的候选。它们都是**软排序**，不能替代冻结、权限或并发硬约束，也不保证计费正确、额度不超用或最优成本。

管理员在「模型路由」打开一个真实模型 → 选择“按调用量”或“按额度节奏” → 查看窗口/信号限制与候选状态 → 保存并处理版本冲突 → 新请求使用新策略；需要回退时选回轮询、优先级或首 Key。对已有会话，只要缓存粘滞目标仍合格，优先保持上游缓存，信号变化本身不强制切换。额度未知时服务继续按明确的降级规则选路，UI 显示原因而不是显示假 0% 或 100%。

**不做**：预测 token 或上游真实扣费、为调用方设预算、额度预扣/保证、跨进程或多实例全局配额、自动更换模型、嵌套组/意图识别；不修改既有 `primary/fallback` 结构。CPA 内部多账号的归属不明时不猜某个账号对应哪把 Key；暂不将响应头或 CPA 被动采样作为 pace 信号。

## 3. 配置和数据模型（均为提案）

配置沿用现有 v4 的模型路由，不新增路由层。示例仅示意相关字段：

```json
{
  "models": {
    "example-model": {
      "routing_mode": "pace",
      "quota_routing": {
        "usage_window_seconds": 3600,
        "pace_max_age_seconds": 300
      },
      "targets": [
        {"provider": "provider-a", "key": "main"},
        {"provider": "provider-b", "key": "backup"}
      ]
    }
  }
}
```

- `routing_mode` 新增 `usage`、`pace`，仍可由模型继承顶层 `routing_mode`；旧配置缺省仍为 `round_robin`。仅最终选中的**真实模型**使用其策略；unified、任务及端点计划仍先按原规则解析目标，点名 Key 则不排序。
- `quota_routing` 为模型可选对象，未写时使用默认值；它不是开关，也不会替代 `routing_mode`。参数为整数：`usage_window_seconds` 默认 3600、范围 60..3600 秒；`pace_max_age_seconds` 默认 300、范围 120..3600 秒。未知字段、null 成员、非整数、越界拒绝保存并标出字段，不静默截断。对象整体在旧三模式下保留但不生效，切回后恢复。
- 运行时目标需同时携带**模型内展开名**与**原始供应商 Key 坐标** `(provider_id, provider_key_name)`；前者维持点名/重试和兼容，后者用于订阅信号及 usage 归属。对同一物理目标多次绑定，使用该坐标共享 usage；不同坐标不靠名称或邮箱猜成同一个额度池。原有账号指纹与供应商并发约束继续各自生效；Key 改名、替换凭据、目标改绑或供应商端点变化时，相关旧采样不能沿用。
- **usage 状态**：进程内按原始坐标保存秒粒度、最多 3600 秒的环形计数，以及该坐标的覆盖起点。每次准备好的代理上游请求交给 HTTP 客户端 `Do` 时记 1；包含随后 DNS/连接失败的尝试，成功、失败及重试分别计数，不计排队、预检失败或未调用 `Do` 的请求。这是 AMKR 的发送尝试量，不代表上游实际收到或扣费。所有引用此坐标的模型合计，不依赖访问密钥。服务启动时即为所有配置目标开始采集（即便当前不是 usage 模式，包含显式点名和所有模型），新建或变更身份时从该时刻开始采集。滚动窗口完全位于覆盖起点之后才视为 `known`；服务重启、身份变更或配置窗口加长后覆盖不足时进入 `warming`，等满配置窗口，不把缺失历史算作零。无持久化、无跨进程聚合。内存上界为每个活跃坐标固定 3600 秒桶；删除目标后待最后在途结束，再按窗口过期回收；禁止按请求数无限追加。
- 指标库用于管理端对账，不拿旧历史反推上述状态：现有 metrics 的模型内 Key 名可能不是供应商原始名，且可能缺归属；旧库或未采集段无法安全补齐。实施时应在新尝试指标中**增量**记录原始坐标与采集口径（不改旧列含义），或在 API 明确显示现有 Key 用量仅供参考；缺失/重试/流式等差异不能解释成上游配额。usage 模式刻意选**请求次数**而非 token：调用开始即已知且适用于不返回 token 的端点，但不同请求消耗不同，不能声称按真实额度或真实 token 均衡。
- **pace 快照**：新建进程级不可变快照，键为原始供应商 Key 坐标，值包含信号来源、身份/配置版本、实际观察时刻、适用模型集合、每个完整适用窗口的类型、剩余比例和重置时刻。请求只读快照；不在选路锁内访问数据库、文件或网络。仅接受现有订阅采集的 `OK=true`、`source=quota` 的主动窗口，并要求供应商适配器能证明窗口对该目标上游模型适用、所需窗口集合完整、采样时间可靠。未实现该证明的供应商、模型分组不明、CPA 内部多账号或只来自被动数据的条目均是 `unknown`；不得因同 base URL、同名或 group 标签猜映射。v1 只处理经 `quota.WindowKind` 明确识别的 5h/7d；其他周期不猜。若一个被证明适用于该模型的完整窗口集合还包括未支持的周期，则整个候选为未知，不得只丢弃未知周期后声称其余窗口完整。现有 OpenCode Go 采集含 rolling、weekly、monthly 三类（`internal/api/subscriptions.go:332-349`、`internal/api/subscriptions.go:363-377`），其 monthly 是否约束目标需先核实；v1 不据此暗示它已经能产生已知分数。
- 当至少一个模型启用 pace 时，拟复用现有账号资源的扇出，服务端按 60 秒周期采样；与冻结巡检/页面采集对同一轮做合并，避免重复并发扇出。若上一轮尚未结束则跳过本轮而不排队，继续保留有效旧结果；停用最后一个 pace 模型后不再发起 pace 专属采样，其他功能原有采集不受影响。冻结巡检间隔为 0 时，pace 的采样仍可运行，但**不得**因此启用自动冻结或修改现有冻结；实现需把共享采集与 QuotaGuard 的“是否应用冻结”拆开。完成一轮后按条目真实 `observed_at` 更新，不能用整屏 `fetched_at` 给旧/被动数据续命。单条失败只影响该条，保留旧快照至自然过期，记录错误分类；成功但缺适用窗口视为未知。没有足够身份/模型证据时宁可全未知。

## 4. 选路次序和精确算法（提案）

### 4.1 资格先于排序

1. 按现有规则解析模型/工作空间和访问凭据；过滤未启用及作用域外目标，再执行额度冻结及其阈值白名单规则。显式 `model[key]` / 计划固定 Key 不参与新排序，但仍走原有鉴权、冻结、并发约束。
2. `only_first` 保持第 2 节的原样分支：只认允许范围内配置顺序第一把；不能因其额度分数低、信号未知、冻结或并发满而改走第二把。除本提案明确的跨代并发修正外，旧三模式不启用新排序。priority/round_robin 的既有选择和粘滞语义不因安装新版本改变。
3. 对 usage/pace 走普通模式现有过滤：重试排除集、冻结、欠费、并发上限均不能被排序或粘滞绕过；先排除冷却，如无剩余候选才按现有规则**仅**软放宽冷却。全冻结、无可用、并发满等仍使用既有错误及代理映射；如先前尝试已得到上游响应，保留当前重试与错误返回语义，不新增重试或改变模型 fallback。
4. 在剩余候选中先查现有粒度的缓存粘滞。如果目标仍在上述可用集合，则直接获取并复用，即使它分数不最高、信号未知或其他 Key 更空闲；只有不可用/被排除时删除该条映射并重新排序。新选出目标写回映射。若请求没有有效 affinity 则正常排序；这里的优先是软偏好，不能突破硬过滤。

### 4.2 usage：最少已发调用优先

对每个候选 `i`，以一次选择捕获的同一时刻 `now` 和模型配置窗口 `W` 计算：

```text
n = floor(now 的 Unix 秒)
started_i = 秒号属于 [n-W+1, n] 的已发出上游 HTTP 尝试次数
pending_i = 已获取该目标、但尚未真正发出 HTTP 的预留数
usage_score_i = started_i + pending_i                   # 越小越优
```

`started` 按原始 Key 坐标跨模型合计；`pending` 防止并发请求在首次发送前都选到同一项。在首次调用 `Do` 前在同一共享状态锁中将一次 pending 转为 started（不是两次计数）；同一获取期间若协议回退等再次调用 `Do`，每次独立加 started，不再减少 pending。获取后预检/取消而未调用 `Do` 则只释放 pending。现有一次 `executeAttempt` 内可能多次调用 `sendUpstream`（`internal/proxy/retry.go:297`、`internal/proxy/retry.go:361`、`internal/proxy/retry.go:467`）；实现应在每次真正交给客户端的统一入口记数，不应只在选 Key 时记一次，也不计单独的能力探测。秒桶以发出瞬间的 Unix 秒向下取整；W 个桶包含当前秒和此前 W-1 秒，较精确滚动窗口的左边界最多提前丢失不足 1 秒数据，已明确接受该近似。每桶携带秒号避免环形复用旧数据；观察到系统时钟回拨时清空计数并重置覆盖起点为 warming。等分数先选全模型合计**当前在途最少**者，再按模型游标在同分候选中轮转。达到目标并发上限之前，usage 仍只是请求次数分摊，不推测每次耗费 token。

### 4.3 pace：窗口剩余节奏优先

一个窗口有效须同时满足：比例是有限数且在 0..1；观察时刻非未来、距离 now 不超过 `pace_max_age_seconds`；重置时间可解析且晚于 now；`0 < reset_at - now <= 窗口时长 D`；窗口确知属于当前模型且该适配器要求的适用窗口齐全。5h 的 D=18000 秒，7d 的 D=604800 秒。缺比例、缺重置、过期、重置已到、时间异常、采集失败后过期、组/身份不确定均为未知，不把过期值复位成满额。

对于每个有效的适用窗口 `w`：

```text
remaining_time_w = max((reset_at_w - now) / D_w, 1 / 300)
pace_w = remaining_fraction_w / remaining_time_w
base_i = min(8, min(pace_w for w in all applicable windows of i))
pace_score_i = floor(1000 * base_i / (1 + inflight_i))   # 越大越优
```

这里 `inflight_i` 是该原始目标坐标跨模型、跨有效运行时代的在途获取数，包含仍在输出的流。取最紧窗口避免只看 5h 忽略 7d；时间分母下限与分数上限只防临近重置时数学爆炸，不意味着能在重置前用完。整数分数决定同分，先选在途最少，再按模型游标轮转。所有窗口以一次选择的同一 `now` 计算；不得比较绝对金额、不同单位或未确定适用范围的数据。快照是上游观察值，其他客户端调用、采集延迟和在途请求使其可能偏旧，即使分数很高也可能被上游拒绝。

例：A 的 5h 剩余 80%、剩余时间 20%、在途 0，分数 4000；B 剩余 40%、剩余时间 80%、在途 0，分数 500，先选 A。若 A 在途 1，则其分数 2000；并发增加会持续降低其排名。若 A 同时有可信 7d 窗口且其节奏为 0.3，则取 0.3，不忽略紧窗口。

### 4.4 未知信号、同分与探索

候选始终先经过资格/粘滞；信号 `unknown`、`warming`、`stale` 均不是零或满额度。

- 全部未知：对**当前合格集合**按现有 round_robin 思路选择最低在途并游标轮转，不新增失败。先前没有命中粘滞的请求，选中后仍建立相同作用域的粘滞。
- 已知和未知混合：非粘滞选择的每个模型维护一个从 0 开始的序号，每次混合决策加 1；序号为 10 的倍数时在未知组内按最低在途/游标选，否则按已知组公式选。选择及计数在共享锁中完成。未知组为空时不使用该探索分支；粘滞命中不推进序号。因此不能保证已有粘滞会话一定被探索，且探索并非安全探测，也不保证未知候选有额度。
- 任何组内同分都按在途、原配置顺序所构成的循环游标决胜，不依赖 map 遍历、随机数或浮点相等；重启/删除模型后游标可从 0 开始。排序不改变硬过滤结果，单候选仍正常使用。

## 5. API 与 UI 契约（提案）

复用 `GET/POST /api/routes` 和 `GET/PUT /api/routes/{route_id}`：响应中的 `route.routing_mode` 可为新枚举，`route.quota_routing` 原样输出显式配置（未配置可省略，UI 以第 3 节默认值展示）；`config_revision` 沿用现有响应。示例为局部更新，不应清空 targets 或 endpoints：

```json
{
  "config_revision": "<上次读取的版本>",
  "routing_mode": "pace",
  "quota_routing": {"usage_window_seconds": 3600, "pace_max_age_seconds": 300}
}
```

PUT 中省略 `quota_routing` 表示不改；传 `null` 清除整个对象、恢复默认；传对象为**完整替换**而非逐字段合并，对象省略的成员使用默认值。原有 `targets: []` 的删除语义不变；错误请求及 revision 冲突不能写入部分配置。POST 可选带同形对象，`201` 后返回路由与新 revision；PUT 成功返回 `200` 与更新后路由/revision，冲突 `409`，沿用现有路由操作非法模式 `422`（`internal/configops/models.go:243-246`、`internal/configops/models.go:340-345`），新增参数的类型或范围错误定义为 `400`，未授权走现有 `401`；旧客户端省略 revision 的兼容规则不变，新 UI 必带 revision 并在 409 时提示刷新比较，不自动覆盖。

拟新增仅供完整管理权限使用的 `GET /api/routes/{route_id}/quota-routing-status`，不触发采集、冻结评估或改变游标，仅返回内存快照与当前配置解释，`Cache-Control: no-store`。示意响应：

```json
{
  "model_id": "example-model",
  "routing_mode": "pace",
  "as_of": "2026-01-01T00:00:00Z",
  "candidates": [
    {"target_name": "main", "provider_id": "provider-a", "provider_key_name": "main",
     "availability": "eligible", "signal": "known", "source": "subscription_quota",
     "observed_at": "2025-12-31T23:59:30Z", "score": 4000, "inflight": 0},
    {"target_name": "backup", "provider_id": "provider-b", "provider_key_name": "backup",
     "availability": "eligible", "signal": "unknown", "reason": "unmapped_or_incomplete",
     "source": null, "observed_at": null, "score": null, "inflight": 0}
  ]
}
```

状态查询不存在的模型返回 404；`availability` 区分 `eligible/frozen/cooling/balance_limited/concurrency_limited/disabled`；多种状态同时成立时按 disabled → frozen → balance_limited → concurrency_limited → cooling 展示首个原因，cooling 仍可能在全部冷却时被软回退选用，因此该字段不是资格判定替身；`signal` 为 `known/unknown/warming/stale`，未知不输出伪分数。该视图是**无具体访问凭据、无请求排除集和 affinity 的瞬时管理诊断**，不是下一请求保证命中的预演；分数/资格随后可能改变。旧模式显示模式及候选，但 signal/score 为 null，避免把未使用的计算说成生效。状态 API 只暴露坐标、状态、时间、数值及有限原因枚举，不返回账号邮箱、凭据、指纹、响应头原文或采集错误正文。

UI 在现有模型路由编辑器新增“按调用量（usage）”“按额度节奏（pace）”，按模式展示相应窗口/有效期设置及解释。详情列出来源、更新时间、已知/预热/过期/不支持、当前冻结/并发等；对混合未知显示“部分目标无可靠信号，按规则少量轮转”，全未知显示“暂按轮询”；说明粘滞可能优先于分数、重启后 usage 需预热。明确“调用次数不是上游总额度”“窗口读数可能延迟”，不呈现未校验的省钱、命中率或准确率。新前端必须对未知枚举显示原值并禁止无意覆盖。已经安装的旧前端无法由新代码自动修正：它可能把未知枚举显示为默认并在保存时覆盖，升级前应关闭旧管理页面并同步升级 UI；服务端无法仅凭旧请求可靠区分有意切换模式和误覆盖，故不能声称对旧客户端已提供无损保护。

## 6. 并发、热重载、失败与安全（提案）

### 6.1 原子选择与跨代在途

服务现有热重载会新建池；要让在途惩罚及硬并发上限在跨代时仍可信，实施时新增**进程级共享的获取/释放账本**，由启动装配并注入所有代的 KeyPool，不能仅复制旧池瞬时计数（复制后旧请求释放不到新副本）。账本中的目标预留数、原始坐标在途数、账号指纹在途数和供应商在途数共同受一把锁保护。候选资格、分数所需计数读取、上限检查和获取须在该锁的同一临界区完成；热点路径只读已构建的配置与不可变快照，不做 IO。避免同时持有两个池锁再获取账本；规定单向锁序，快照发布者不持账本锁反取池锁。

获取返回一次性内部租约，**捕获获取时**的模型、目标、原始坐标、账号指纹、供应商及所属状态，不在释放时根据热重载后的配置重新查身份；非流式、流式完成、取消、超时、异常、重试各路径恰好释放一次。首次交给 HTTP 客户端时原子从 pending 转 started，同一次获取内后续每次调用 `Do` 另加一次 started；失败/取消但未调用 `Do` 只释放 pending。旧代已发出的请求允许按它持有的运行时完成；旧代尚未发送的尝试也必须经过共享账本及当前冻结/并发硬约束；新代请求使用新配置。热替换与账本采用同一代际发布屏障：新代发布的线性化时刻起，旧/新代尚未发送的获取都采用新代生效上限；限额下调后已有请求不强杀，在途达到或高于新限额时拒绝新增直到降到限额以下；发送前再次在发布屏障内做身份、冻结与限额校验，并将发送准入线性化：发布前已完成准入的请求可以在随后调用 `Do` 并收尾；发布后尚未准入的请求，若目标移除/停用或身份替换则不得再用旧身份准入。限额下调时已获取的 pending 纳入在途，新准入若发现当前总数已超过新限额则拒绝并释放该租约；恰等上限时不额外占名额的已持有租约可准入。需要为旧代重试增加明确的配置代校验：目标已失效时终止该次尝试并走既有错误/fallback，不擅自重复已发送的请求。此边界不保证已准入请求的网络字节必然先于配置保存完成发出。

这是一项**明确的兼容修正**：跨热重载重叠期间旧实现各池各计数，提案将各模式的 Key/供应商上限统一为进程内跨代上限，可能比旧版更早返回 429；稳定配置下旧模式选路语义不变。密钥/目标替换时账本保留旧租约直至归还，不能把旧请求错记到新 Key。共享 usage 状态以原始坐标及凭据/端点身份版本校验；快照发布前确认身份仍是当前配置，丢弃迟到的旧采样。无可靠身份继承时状态重置为未知/预热，粘滞允许重建；不把这种重置说成保留原缓存命中。

### 6.2 故障和安全边界

- 配置非法：管理接口拒绝并保留旧配置；手工写坏的文件沿现有配置加载/热重载失败路径保留当前有效运行时，不切换到半成品。采集超时/返回缺失/队列忙：不阻塞推理，沿用未过期快照，过期后进入未知，冻结规则仍独立生效。
- 冷却仅按现有软回退；冻结、余额不足（普通模式）及并发满不因无信号而放行。全冻结沿既有 503、全并发阻塞沿既有 429；其他错误及已有 fallback 顺序不由新策略改写。
- 管理配置/诊断只允许现有 full 管理凭据；工作空间面板凭据、受限访问密钥及匿名用户不能读跨账号诊断或写策略。推理接口不新增可由调用方控制的采集地址、模式覆盖或额度字段。只访问既有受控配置对应的采集端点，不将用户输入拼成 URL。
- 内存只保留排序所需数据；日志和状态仅有限原因码及脱敏坐标，不输出上游/本地 API key、账号邮箱、请求体、原始响应头或凭据指纹。采集错误不得直接回显上游响应正文；限制日志频率，避免故障刷屏。管理接口禁缓存；不通过推理响应头暴露其他 Key 的额度或分数。
- 单进程内可串行化；多进程/多副本各有本地账本、调用计数和样本，无法保证全局并发、额度均衡或不超额。进程崩溃丢失内存计数，重启走预热/未知，不伪称恢复历史。监控可聚合按模式的选择、降级、未知和采集失败计数，不能带密钥/高基数账号标签；调试时以管理状态解释具体目标。

## 7. 端到端验收矩阵（拟实现后执行，本次未执行）

| 场景 | 操作与可判定结果 |
| --- | --- |
| 旧配置兼容 | 缺字段及三种旧模式加载；稳定配置下相同候选、粘滞、冷却、错误和点名行为保持；不默认启用 pace 外部轮询；本地 usage 秒桶会从启动即记数，但不改变旧模式选路结果。 |
| 配置/管理并发 | 用完整权限读取 revision 后保存两种新模式及边界值；错误类型/越界拒绝，旧 revision 返回 409 且磁盘和运行态无部分更改；省略对象不改、null 恢复默认。 |
| 权限与数据 | 匿名、受限访问密钥、工作空间面板凭据尝试读诊断或写策略被拒；完整权限可读；响应和日志不含密钥、邮箱、指纹及错误原文。 |
| usage 与 warmup | 可控时钟先建立完整窗口，A 上游请求调用 `Do` 2 次、B 1 次且无粘滞/在途时选 B；未调用 `Do` 的取消不计，DNS/连接失败计一次，同次获取中的协议回退和重试分别计；重启或换凭据后未覆盖整窗为 warming，不当成 0。 |
| usage 并发 | 多并发获取时 pending 随选择原子增加，出网转换不重复计；流式/非流式/失败/取消/超时均各释放一次；相同坐标跨模型合计，模型内别名能映射原始坐标。 |
| pace 公式 | 使用第 4.3 节 A/B 数字复现 4000/500；A 同时存在 0.3 的 7d 窗口时取 0.3；加入在途后分数按公式下降；整数同分先最低在途再轮转。 |
| 未知/探索 | 信号缺失、过期、reset 已到、无组归属或 CPA 多账号时均未知；全未知 RR；混合时第 10 次非粘滞选择从未知组取；无越权/冻结/并发穿透。 |
| 采集与冻结 | 开启 pace 而冻结巡检关闭时可以采样但不产生新冻结；采集失败不影响已有冻结、不将旧快照续期；冻结硬耗尽不被阈值白名单或未知降级绕过。 |
| 粘滞和重试 | 即便新分数更高，合格粘滞目标仍优先；其冻结、并发满、排除或硬欠费时重新选合格目标；重试预算、上游返回和模型 fallback 不变。 |
| only_first/点名 | 第一把冻结或并发满直接失败，不因第二把高分改道；点名 Key 不排序，冻结和并发限制仍有效；普通模式的冷却软回退不套用到 only_first。 |
| 热重载重叠 | 长流占额时改变模式、调低限额或删除/改绑 Key：新旧代共享在途账本，直到旧流结束才释放旧身份；不得双扣/误释放，新目标不继承旧信号；旧代尚未完成发送准入的尝试不能使用已停用身份，已准入的尝试允许完成。 |
| UI / 升级回退 | 新模式保存后刷新仍显示配置、来源与未知原因；新前端对未知枚举禁止误覆盖，已安装旧前端的误覆盖风险在升级提示中明确；回切 round_robin 后新排序不生效；运行态诊断不承诺下一次请求具体落点。 |

以上为验收方案，不表示已经实现或测试。应由独立 QA 按实际用户操作验证正常、失败及热重载路径，并用可控时钟与假上游覆盖算法边界；不要为了凑数量新增无效测试文件。
